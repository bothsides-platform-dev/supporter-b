# 전자계약 법적 효력·상용 패턴 딥리서치 (2026-07-17)

전자계약(e-contract) 기능 설계의 근거 리서치. 딥리서치 워크플로(5축 검색 → 소스 수집 → 클레임 추출 → 3-표 교차검증 → 합성)로 수행했다.

> **검증 상태 캐비앗**: 5개 검색 축 중 1축(법적 토대)은 완주, 3축(기술 구현·상용 비교·비용)의 검색 에이전트와 25개 클레임 전체의 3-표 교차검증 단계가 **인프라 사유(API 연결 중단·세션 한도)로 실패**했다. 아래 클레임은 모두 "미검증(unverified)"이며 **반박된(refuted) 클레임은 없다**. 다만 핵심 법령 클레임의 출처가 법령 원문(law.go.kr)·정부 운영 사이트(공인전자문서센터 npost.kr) 등 1차 출처라 실무 신뢰도는 높다. 조문 번호는 인용 시 원문 재확인을 권장한다.

## A. 전자서명법 (2020 전부개정 이후 현행)

- **A-1. §3① 비차별 원칙** — 전자서명은 전자적 형태라는 이유만으로 서명·서명날인·기명날인으로서의 효력이 부인되지 않는다. [S1]
- **A-2. §3② 약정 기반 효력** — 법령 규정 또는 **당사자 간의 약정**으로 전자서명을 선택한 경우 그 전자서명은 서명·서명날인·기명날인의 효력을 가진다. §3은 이 두 항이 전부로, 특정 기술(공인인증서 등)에 우월적 효력을 부여하는 조항이 없다 → **B2B 플랫폼이 자체 구축한 전자서명도 당사자 간 약정이 있으면 서명으로서의 법적 효력을 갖출 수 있다.** [S1]
- **A-3. §2 제2호 정의는 기술 중립** — (가) 서명자의 신원과 (나) 서명자가 해당 전자문서에 서명하였다는 사실을 나타내기 위해 전자문서에 첨부되거나 논리적으로 결합된 전자적 형태의 정보면 전자서명이다. PKI 인증서·특정 암호기술을 요구하지 않는다 → 자체 구축 시 최소한 이 두 요소(신원 표시 + 서명 사실)를 입증 가능하게 남겨야 한다. [S1]
- **A-4. §8 운영기준 준수사실의 인정 = 임의 제도** — '인정을 받을 수 있다'로 규정된 선택 제도이며, 인정 없이도 전자서명 자체의 효력(§3)은 성립한다 → **RFP 매칭 플랫폼이 자체 전자계약 기능을 제공하기 위해 인정사업자가 될 법적 의무는 없다.** [S1]
- **A-5. §18 전자문서 시점확인(타임스탬프) = 임의 서비스** — 전자서명인증사업자가 요청 시 제공할 수 있는 서비스일 뿐, 모든 전자계약에 TSA 타임스탬프를 법적 성립 요건으로 요구하지 않는다. [S1]
- **A-6. 2020.12.10 전부개정으로 공인인증서 제도 폐지** — 1999년 이래의 법적 독점 구조가 사라지고 민간 전자서명 수단이 동등한 지위에서 경쟁. 입법 취지는 공정경쟁 환경 조성을 통한 산업경쟁력 제고와 국민 선택권 보장. [S4][S6]
- **A-7. 실지명의(실명) 확인 권한의 제약** — 개정 후에도 인증제도가 구 공인인증기관·본인확인기관 중심으로 설계되어, **지정된 본인확인기관이 아닌 사업자는 주민등록 기반 실명확인을 직접 수행할 법적 권한에 제약**이 있다(학계는 인정사업자 실지명의 확인 권한 확대를 개선방안으로 제시). → 자체 구축의 신원확인은 '이메일+계정' 수준이 현실적 상한이며, 실명확인 강화는 외부 본인확인기관 연동이 필요하다. [S4]

## B. 전자문서 및 전자거래 기본법

- **B-1. §4① 전자문서 효력 부인 금지** — 전자문서는 전자적 형태라는 이유만으로는 법적 효력이 부인되지 않는다(다른 법률에 특별한 규정이 있는 경우 제외). 전자계약서를 전자문서로 작성해도 그 자체로는 효력 문제가 없다. [S2][S3]
- **B-2. §4의2 서면 인정 요건** — 전자문서가 '서면'으로 인정되려면 (1) 내용의 열람 가능성과 (2) 작성·변환·송수신·저장 당시의 형태(또는 재현 가능한 형태)로의 보존이 필요하다 → 문서 무결성·재현성·보존 아키텍처가 이 요건을 충족해야 한다. [S2]
- **B-3. §5 보관 의무 갈음** — 법정 요건을 갖춘 전자문서 보관은 다른 법령의 (종이)문서 보관 의무를 갈음할 수 있다(타 법령이 달리 정하면 예외). 완료 계약서의 전자적 보관 근거. [S2]
- **B-4. §6 송신 시점** — 작성자(또는 대리인)가 송신 가능한 정보처리시스템에 입력한 후 수신 가능한 시스템으로 전송한 때를 송신 시점으로 규정 → 발송·수신 타임스탬프 기록이 이 시점 입증에 대응해야 한다. [S2]

## C. 민사상 성립·증거력

- **C-1. 낙성·불요식 원칙** — 민사상 전자계약은 당사자 간 합의만으로 유효하게 성립하며, 서명 형식 요건은 계약 성립 요건이 아니다. 전자문서의 증거력은 **법관의 자유심증주의**로 판단된다. [S5]
- **C-2. 법적 신뢰성 3요소** — ① 서명자의 신원을 확인하고 해당 전자문서에 서명했다는 사실을 나타낼 수 있을 것 ② 서명 생성 당시 전자서명 생성정보가 서명자의 유일한 지배하에 있을 것 ③ 서명 후 전자서명·전자문서의 변경 여부를 확인할 수 있을 것(무결성 검증 가능성). [S5]
- **C-3. 방어력의 3단계 구조** — (1) 전자서식 솔루션의 서명 행위 자체로 기본적 증거능력 확보 → (2) 인증기관·간편인증 연동으로 서명자 실지명의 증거능력 보강 → (3) 감사추적인증서 관리·검증으로 생성부터 폐기까지 전 과정 기록·보관. 자체 구축의 최소 구현 vs 권장 구현 층위에 대응. [S5]
- **C-4. 감사추적인증서 포함 항목** — 문서 식별 정보, 작성자·수정자 정보, 생성·수정·전송·수신 시간, 행위의 종류(열람·수정·서명 등). [S5]

## D. 상용 서비스 패턴 (모두싸인)

- **D-1. 법적 효력 안내 구조** — 전자문서법 §4①을 효력 근거로, 전자서명법 §3②(당사자 약정)를 서명 효력 근거로 안내. 흥미롭게도 헬프센터 인용 조문 텍스트는 2020 개정 이전 구법 문구('공인전자서명 외의 전자서명은…')로 남아 있다 — 취지는 현행법과 동일(약정 기반 일반 전자서명의 효력 인정). [S3]
- **D-2. 감사추적인증서 운영** — 서명 진행의 중요 시점마다 **시간(타임스탬프)·IP 주소·기기 정보·브라우저 정보**를 감사 로그로 기록하고, 체결 완료 후 이 로그가 담긴 인증서를 **계약 당사자 전원의 이메일로 발급·전송** + 서비스 내 열람 제공. '해당 행위를 했다는 사실'의 증명 수단. [S3]
- **D-3. 본인확인 3단계 옵션** — 기본 = 이메일 인증. 추가 옵션 = 모바일 인증(카카오·네이버·토스 앱 또는 통신사 등록 정보 기반 실명 확인), 접근 암호 인증(국내 휴대폰 실명인증이 어려운 경우의 대체). [S3]
- **D-4. 간인·계인의 대체** — 종이계약의 간인·계인은 전자서명에서 불필요하다고 안내하며 대체 수단으로 ① 각 페이지 좌측 하단 **문서ID**(간인 대체 — 연속된 하나의 계약서임을 확인) ② 문서별 **원본 검증키 + 위변조 검증센터**(계인 대체)를 제시. 근거 판례로 **대법원 2021.12.30. 선고 2019도16259 판결**(간인 없는 공소장도 형식·내용의 연속성과 작성자 동일성이 인정되면 유효 — 형사 공소장 사건의 유추 적용)을 인용. 단 자사 문서는 계약 성립의 법적 증거일 뿐 **내용증명·공정증서와 동일한 효력은 아니라고 명시**. [S3]

## E. 한계·주의

- **E-1. 전자계약 활용 제한 문서** — 부동산 등기 신청서, 공증을 요하는 문서(유언장 등), 법원 제출 서류는 전자계약 활용이 제한된다. (본 플랫폼의 B2B 용역계약은 해당 없음) [S6]
- **E-2. 근거 없는 체크리스트 주의** — '타임스탬프 포함·서명 이력·수정 불가 처리'를 플랫폼 선택 기준으로 제시하는 업계 글은 법령·판례 근거를 인용하지 않는 경우가 있다(방향은 C-2·C-4와 정합). [S6]
- **E-3. 출처 간 조문 혼동 사례** — 전자문서 효력 부인 금지의 근거를 전자서명법 §3으로 표기한 글이 있으나, 실제로는 전자문서법 §4①이 전자문서, 전자서명법 §3이 전자서명의 효력 조항이다(수집 단계에서 식별된 반증 가능 진술). [S6]
- **E-4. 커버리지 공백(정직 고지)** — 검색 에이전트 실패로 ① 판례 심층(간인 판례 1건 외 전자계약 증거력 판례), ② PAdES/PKI vs 시각적 스탬핑의 국내 법적 평가 문헌, ③ 국내 전자서명 API(모두싸인 API·eformsign 등) 요금·기능 비교는 이번 리서치에서 확보하지 못했다. 자체 구축 결정은 A-2~A-5(법령상 요건·의무 부재)로 정당화되며, PAdES/TSA·실명인증은 증거력 '보강' 수단으로 후속 과제(TODOS)에 기록한다.

## F. 설계 반영 (요건 → 구현)

| 법적 요건 | 근거 | 구현 |
|---|---|---|
| 당사자 약정 | A-2 | 서명 시 전자서명 동의 체크 필수 — 동의 문구 전문·버전(`consent_text_version`)·시각을 서명자 행에 보존, 확인서(별지2)에 렌더 |
| 신원 + 서명사실 (§2-2호) | A-3, C-2① | 이메일 인증 계정 + 워크스페이스 멤버십 + **지정 서명자 본인만** 서명 가능. 서명 이미지·일시·IP·UA 를 확인서에 결합 |
| 서명자 지배 | C-2② | 세션 인증 하 클릭투사인 (밖에서 재현 불가) |

| B2B 체결 권한 | (관행) | 동의 문구에 "소속 회사를 대표하거나 적법하게 위임받아 체결할 정당한 권한" 확인 포함 |
| 감사추적 | C-4, D-2 | `contract_doc_events`(시간·IP·UA·행위: 발송/열람/서명/재지정/완료/반려/회수/만료) + 최종 PDF [별지2] 확인서 + 완료 이메일 |

| 송신 시점 | B-4 | 발송(sent_at)·수신·서명 서버 타임스탬프 기록 |
| 한계 고지 | A-7, D-3 | 신원확인은 '이메일 기본 인증' 레벨임을 문서화. 모바일 실명인증·PAdES/TSA 는 후속 확장(TODOS) |
