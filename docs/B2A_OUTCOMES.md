# B2A 계약·연동·수수료 결과 연결

2026-11-09 · v0.50.0.0. 제휴사가 확인한 결과를 기존 에이전트 상담과 연결한다. 운영 배포·실제 제휴사 계약·수수료 수령을 완료했다는 뜻은 아니다.

## 무엇을 기록하나

| 기록 | 의미 | 필수 근거 |
|---|---|---|
| `provider_contract_confirmed` | 고객과 선정 PG의 서비스 이용계약 확인 | 제휴사 확인 또는 운영 확인 자료 |
| `integration_verified` | 테스트/운영 환경의 연동 확인 | 시험 결과·제휴사 확인·운영 확인. 고객 제보는 별도 `reported` 상태 |
| `commission_confirmed` | 서포트비가 받을 수수료 확정 | 제휴 계약 참조·산정 근거·통화·확정액 |
| `commission_paid` | 실제 수령한 수수료 기록 | 지급 근거·해당 확정 기록·통화·수령액 |
| `voided` | 잘못 입력한 기록의 무효화 | 대상 기록·정정 사유·근거 |

`contracts`는 기존 견적 선정 기록이며, 노온–구매사 합의서도 PG 서비스 계약 증명이 아니다. 서비스 이용료·거래액·구매사 PG 요율로 서포트비 수수료를 추정하지 않는다. 수수료는 제휴 조건에 따라 확인한 금액을 입력한다. 이 도구는 계약 체결·송금·환불·제휴사 연락을 실행하지 않는다. 이용·해지·환불 정책은 각 제휴사 조건을 따른다.

현재는 선정까지 끝난 PG 상담이 대상이다. 패키지·클라우드의 다중 제휴사 거래 모델은 이후 별도 설계한다.

## 운영자 사용법

DB 접근 권한이 있는 운영자 환경에서 `DATABASE_URL`을 주입한다. 환경 파일은 자동으로 읽지 않는다. `--operator`는 감사용 입력 표식이며 인증된 관리자 신원이 아니다. 별도 관리자 웹에 연결할 때는 전용 쓰기 권한(예: `partner_outcomes.edit`)을 검사해야 한다. 현재는 고객용 HTTP API나 MCP 쓰기 도구를 제공하지 않는다.

입력은 최대 16KiB UTF-8 JSON이다. 아래 UUID·참조는 형식 설명용 예시이므로 실제 상담·선정 PG·확인 자료에 맞게 바꾼다. 인증정보·원문 계약·결제정보·개인정보를 넣지 않고 내부 보관소의 짧은 참조 번호를 쓴다. 참조는 영문·숫자·점·밑줄·슬래시·하이픈만 허용하며 URL은 받지 않는다.

```json
{
  "commandId": "11111111-1111-4111-8111-111111111111",
  "requestId": "22222222-2222-4222-8222-222222222222",
  "providerWorkspaceId": "33333333-3333-4333-8333-333333333333",
  "kind": "provider_contract_confirmed",
  "reference": "pg-contract-20261109-001",
  "source": "partner_confirmation",
  "evidenceReference": "partner-evidence/001",
  "occurredAt": "2026-11-09T10:00:00+09:00"
}
```

```sh
pnpm b2a:outcomes record --file /secure/contract.json --operator ops-member
pnpm b2a:outcomes record --file /secure/contract.json --operator ops-member --execute
pnpm b2a:outcomes inspect --request 22222222-2222-4222-8222-222222222222
```

첫 명령은 DB에서 관계·중복·금액을 검증하지만 기록하지 않는다. `--execute`에서 다시 검증하며, 미리보기의 임시 `entry.id`는 저장된 ID가 아니다. **실행 결과의 `entry.id`**를 후속 지급·정정의 `relatedEntryId`로 사용한다. 출력에는 내부 근거와 금액이 포함되므로 운영자 범위에서 보관한다.

다른 기록은 공통 필드를 유지하고 다음 필드를 추가한다. 새로운 사실은 새 `commandId`와 `reference`, 응답 유실에 따른 동일 작업 재시도는 기존 값을 쓴다.

| kind | 추가 입력 |
|---|---|
| `integration_verified` | `integrationEnvironment`: `sandbox` 또는 `live` |
| `commission_confirmed` | `amount`: 문자열, `currency`: `KRW` 등 3자리 대문자, `agreementReference`, `calculationReference`. 산정 기간은 `periodStart`·`periodEnd`를 모두 `YYYY-MM-DD`로 입력하거나 모두 생략 |
| `commission_paid` | `relatedEntryId`: 확정 기록 ID, `amount`, `currency` |
| `voided` | `relatedEntryId`: 취소할 기록 ID, `reason`: 1~300자 정정 사유. 개인정보 없이 작성 |

금액은 `"125000.5000"`처럼 문자열로 입력한다. 최대 정수 16자리·소수 4자리이며 부동소수점 계산을 하지 않는다. 확정액 0은 명시적으로 기록할 수 있지만 지급액은 0보다 커야 한다. 여러 회차의 확정·부분 지급을 지원하며 통화가 다르거나 누적 지급액이 확정액을 넘으면 거부한다. 근거 source는 `partner_confirmation`, `operator_evidence`, `partner_api`이고, 연동에만 `customer_report`, `test_result`도 허용한다. `partner_api`는 향후 어댑터도 사용할 수 있는 출처 이름이며 지금 자동 조회하는 기능은 아니다.

## 무결성과 정정

- 발송된 요청 → 구매사 워크스페이스 → RFP → 선정 견적·선정 PG의 실제 관계를 확인한다. 후보 PG를 계약 상대방으로 간주하지 않는다. OAuth 철회·만료는 이미 발송된 거래 결과 기록을 막지 않는다.
- RFP 행 잠금 안에서 검증·추가·내부 `admin_audit_logs` 감사를 함께 커밋한다. 같은 `commandId`와 같은 정규화 입력은 기존 결과를 반환하며 다른 입력은 충돌이다. PG·종류·참조 번호 중복도 거부한다.
- 계약 확인 후 수수료를 확정하고, 해당 확정 기록에 지급을 연결한다. 발생 시각은 발송·선행 기록보다 빠르거나 미래일 수 없다. 실제 발생 시각과 서버 기록 시각을 따로 저장한다.
- 기존 행을 덮어쓰거나 지우지 않는다. 지급이 있으면 지급 정정 → 수수료 확정 정정 → 필요 시 계약 확인 정정 순서다. 정정 뒤에는 새 명령·참조로 올바른 사실을 기록한다. `voided`는 데이터 정정이며 계약 해지나 환불 처리가 아니다.
- 결과는 `partner_outcome_entries`에 보관한다. 원래 요청의 생성 시각·환경을 스냅샷으로 남기며 기존 환경이 없으면 `unknown`이다. 실행 셸의 환경으로 과거 성과를 운영 실적으로 바꾸지 않는다.
- OAuth 연결/요청 물리 삭제 시 `request_id`만 NULL로 바뀌고 RFP 귀속·금액·근거·감사는 남는다. RFP와 제휴사 워크스페이스 물리 삭제는 FK로 막는다. 물리 삭제된 요청은 현재 CLI로 추가 기록/조회할 수 없으므로 거래 종료 전에는 연결 철회를 사용한다. 법적 보존·삭제 절차는 운영 정책과 함께 별도로 결정한다.

## 에이전트와 분석에서 보이는 값

`get_request_status`와 같은 요청 조회는 기존 연결 소유권 검증 후 계약·연동의 상태, 확인 시각, 기록 시각, 출처만 반환한다. 계약은 `confirmed`/`not_verified`, 연동은 환경별 `verified`/`reported`/`not_verified`다. 고객 제보만으로 연동 성공을 확정하지 않는다. 내부 수수료·근거 번호·정정 사유·기록 주체는 에이전트에 전달하지 않는다.

기존 `pnpm b2a:analytics report`의 JSON·Markdown·HTML에 다음 집계를 추가했다.

- 기간 내 만들어진 요청에 연결된 계약·운영 연동·테스트 연동·고객 제보·수수료 확정·지급의 RFP별 개수.
- 통화별 확정액·지급 기록액·남은 금액. 통화 사이 환산이나 합산은 하지 않는다.
- 종료 시각 전에 **발생하고 기록된** 사실만 포함한다. 종료 후 입력한 과거 사실이나 정정은 이미 지난 기준 시각의 결과를 소급해 바꾸지 않는다.

이는 해당 요청 집단의 확인 기록이며 그 기간 전체의 회계 매출이나 입금 내역이 아니다. 기록이 없다는 것은 미확인이다. 연결을 물리 삭제하면 연결·초안 집계는 사라지지만 결과 원장은 유지되므로 두 집계를 단순히 나눠 전환율로 쓰지 않는다. 장기 비교는 동일 집계 기준으로 내보낸 리포트를 이용한다.

## 배포 순서와 후속 범위

기존 계정 채널 DDL → [분석 DDL](../scripts/migrations/20261108-agent-analytics.sql) → [결과 원장 DDL](../scripts/migrations/20261109-partner-outcomes.sql) → 앱 배포 순서다. 이미 적용한 DDL은 재실행하지 않는다. 새 원장은 분석 선택 수집 플래그와 별개이며 앱 롤백 시에도 보존한다.

현재 작업 범위는 로컬 구현·검증·브랜치 커밋과 푸시다. 운영 배포, 실제 제휴사 근거·수수료 대조, 관리자 웹, 발견 경로 등록, SDK·패키지는 사용자와의 후속 대화에서 진행한다.

## 검증 기록

분석·OAuth·MCP·브라우저·원장·DDL·CLI·버전·저장소 경계를 포함한 관련 30개 파일의 301개 테스트를 통과했다. 금액 정밀도, 중복/초과 지급, 정정 의존성, 감사 실패 롤백, 연결 삭제 후 보존, 다른 연결의 접근 거부, 내부 금액 비노출을 검증했다. 기록 시각은 RFP 잠금·의존성 검증 후 DB 시각으로 생성하며 지연된 지급이 선행 확정보다 먼저 집계되지 않는 회귀 검사도 포함한다.

격리 Postgres 17에서도 새 DDL·실제 CLI 미리보기→계약 확인→수수료 확정→부분 지급→중복 재시도→HTML 생성을 확인했다. 확정 100에 지급 70 두 건을 동시에 실행하면 한 건만 저장하고 나머지는 초과 지급으로 거부했다. 원장 5행과 감사 5행을 대조하고 기존 시험 상담 2건 보존·production 집계의 시험 데이터 제외도 확인했다. Chromium 1280px·390px에서 계약·수수료 표의 표시와 페이지 가로 넘침 없음을 확인했다. 운영 DB·실제 제휴사 거래는 변경하지 않았다.
