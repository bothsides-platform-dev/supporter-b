# 카카오 알림톡 운영

## 활성화 전제

보유 채널을 SOLAPI에 연결하고 아래 템플릿 7종을 등록·승인받는다. 이 문서는 등록용 문안이며 승인 완료를 뜻하지 않는다. 실제 API 키·발신번호·채널 ID·승인 템플릿 ID는 운영 비밀 설정으로 주입한다. 저장소에는 입력하지 않는다.

| 환경변수 | 등록 문안 |
| --- | --- |
| `SOLAPI_TEMPLATE_OTP` | `서포트비 인증번호: #{인증번호} (5분 이내 입력)` |
| `SOLAPI_TEMPLATE_RFP_INVITED` | `서포트비에 새 견적 요청이 도착했어요. 견적번호: #{견적번호} 요청 확인: #{링크}` |
| `SOLAPI_TEMPLATE_BID_SUBMITTED` | `서포트비에 견적이 도착했어요. 견적번호: #{견적번호} 견적 확인: #{링크}` |
| `SOLAPI_TEMPLATE_REQUOTE_REQUESTED` | `서포트비에 견적 수정 요청이 도착했어요. 견적번호: #{견적번호} 수정 요청 확인: #{링크}` |
| `SOLAPI_TEMPLATE_AWARDED` | `서포트비에서 보내신 견적이 최종 선정됐어요. 계약 탭에서 계약서를 확인하고 서명을 요청해 주세요. 견적번호: #{견적번호} 계약 준비: #{링크}` |
| `SOLAPI_TEMPLATE_AWAITING_CONTRACT` | `서포트비에서 계약서 발송을 기다리고 있어요. 이미 발송했다면 결과를 확인해 주세요. 견적번호: #{견적번호} 계약 확인: #{링크}` |
| `SOLAPI_TEMPLATE_SIGNING_COMPLETED` | `서포트비에서 모든 서명을 완료했어요. 견적번호: #{견적번호} 완료 문서 확인: #{링크}` |

변수 이름은 중괄호를 포함해 코드와 정확히 같아야 한다. OTP는 보안 템플릿의 모바일 표시 특성을 실기기에서 확인한다. 승인 과정에서 문안·변수 변경이 필요하면 코드와 이 문서도 함께 갱신한다.

- [SOLAPI 공식 발송 API](https://solapi.com/developers/api/messages): `showMessageList:true`, `kakaoOptions.pfId/templateId/variables`, `disableSms:false`를 사용한다.
- [보안 템플릿 안내](https://guide.solapi.com/fc4fae25-87de-4f81-81d3-4f940d8c4cc9)

## 배포 순서

1. 운영 DB 백업 후 `scripts/migrations/20261015-alimtalk.sql`을 적용한다. `users.business_alimtalk_enabled`와 `alimtalk_outbox` 및 인덱스를 확인한다. 앱 재시작보다 먼저 적용한다.
2. 기본 `PHONE_OTP_CHANNEL=sms`, `BUSINESS_ALIMTALK_ENABLED=false` 상태로 코드를 배포한다. 기존 이메일·앱 알림은 유지된다. 업무 기능이 꺼진 동안에는 알림톡 큐를 적재하지 않는다.
3. 기존 `SOLAPI_API_KEY`, `SOLAPI_SECRET_KEY`, 등록 발신번호 `SOLAPI_SENDER`와 `SOLAPI_KAKAO_PF_ID`, 템플릿 ID 7개를 설정한다. 서버 전용 변수이며 `NEXT_PUBLIC_` 접두어를 붙이지 않는다.
4. 테스트 환경에서 `PHONE_OTP_CHANNEL=alimtalk` 및 업무 기능을 켜고 운영자가 지정한 테스트 번호·계정으로 아래 수신 검증을 수행한다. 임의의 실제 회원에게 테스트 발송하지 않는다.
5. 검증 완료 후 운영에서도 인증과 업무를 각각 활성화한다. 환경 변경 뒤 PM2를 재시작하고 `/api/cron/flush-outbox`가 기존 1분 cron에서 호출되는지 확인한다.

## 수신 검증 기록

현재 이 구현에서는 실제 발송·템플릿 승인·운영 DB 적용을 수행하지 않았다. 다음 표를 운영자가 채운 뒤 활성화한다. API 접수와 단말 수신을 구분한다.

| 시나리오 | 공급자 메시지 ID | 실제 도착 채널·시각 | 결과 |
| --- | --- | --- | --- |
| 구매사/PG 가입 OTP·프로필 OTP | 미실행 | 미실행 | 미검증 |
| 카카오 수신 불가 테스트 번호의 같은 OTP 문자 대체 | 미실행 | 미실행 | 미검증 |
| 업무 템플릿 6종 알림톡 수신 | 미실행 | 미실행 | 미검증 |
| 업무 문자 대체·수신 해제 후 미발송 | 미실행 | 미실행 | 미검증 |

인증번호는 6자리·5분 만료·10분 내 3회 제한을 유지한다. 명확한 접수 거절은 OTP를 폐기한다. 접수 불명확 시에는 코드를 유지하고 입력 화면을 연다. 서버는 재시도나 별도 문자 발송을 하지 않는다. 사용자 재전송은 새 코드를 생성한다.

## 큐와 복구

업무 사건과 큐 적재는 같은 트랜잭션이다. 중복 키는 템플릿·사건/회차·워크스페이스·사용자 조합이다. 새 견적 요청은 승인된 PG 멤버, 견적 도착은 승인된 구매사 멤버, 수정 요청은 해당 PG 멤버, 선정은 선정 PG 멤버, 서명 완료는 양측 멤버에게 보낸다. 최초 계약 준비는 선정 메시지에 통합하고 이후 계약 라운드와 7일 안내만 별도 발송한다. 채팅·마감·거절·SnowSign 서명 요청은 대상이 아니다.

`pending → sending` 클레임을 DB에서 먼저 커밋한 뒤 발송한다. 커밋 후 worker와 cron은 같은 `FOR UPDATE SKIP LOCKED` 경로를 사용한다. 발송 직전에 수신 설정·계정·이메일 인증·워크스페이스·승인 멤버십·번호를 다시 확인하고, 변경된 대상은 `skipped`로 끝낸다. 나중에 번호를 등록하거나 수신을 켜도 건너뛴 알림은 다시 보내지 않는다.

| 상태 | 의미·조치 |
| --- | --- |
| `pending` | 발송 또는 명확한 미접수 일시 오류의 백오프 대기 |
| `sending` | 발송 클레임 완료. 5분 이상 남으면 다음 worker가 `unknown`으로 바꾼다 |
| `accepted` | SOLAPI가 접수함. 단말 수신 성공이 아님. `message_id`로 콘솔에서 확인 |
| `unknown` | 타임아웃·5xx·응답 해석 실패·프로세스 종료 등 접수 불명확. 자동 재발송 금지 |
| `failed` | 설정 누락·영구 거절 또는 재시도 5회 소진 |
| `skipped` | 발송 전 수신자 조건 변경 |

HTTP 429만 명확한 미접수 일시 오류로 자동 재시도한다. 메시지별 오류는 영구 실패로 두며, 새로운 일시 코드 허용은 공식 근거와 회귀 테스트를 추가한 뒤 한다. 기존 지수 백오프·지터를 재사용하고 최대 5회 시도한다. 5xx나 네트워크 오류는 미접수로 단정하지 않는다.

운영 점검 쿼리:

```sql
SELECT id, template, status, attempts, message_id, last_error, claimed_at
FROM alimtalk_outbox
WHERE status IN ('failed', 'unknown', 'sending')
ORDER BY scheduled_at;
```

`unknown`은 SOLAPI 콘솔에서 시각·수신자·템플릿·메시지 ID를 대조한다. **이미 접수된 건은 절대 `pending`으로 되돌리지 않는다.** 접수되지 않았다는 증거가 있을 때만 운영자가 해당 행 ID를 지정해 `pending`·현재 `scheduled_at`으로 복구하며, 판단 근거를 운영 기록에 남긴다. 확인할 수 없으면 그대로 보존한다. 전체 큐 일괄 재시작은 금지한다. 번호나 본문을 일반 운영 로그에 출력하지 않는다.

## 중단·롤백

- 인증 장애: `PHONE_OTP_CHANNEL=sms`로 변경 후 재시작한다. 이미 발급한 코드는 유효기간 동안 유지된다.
- 업무 장애: `BUSINESS_ALIMTALK_ENABLED=false`로 변경 후 재시작한다. 이메일·앱 알림은 계속 동작한다. 이미 공급자가 접수한 대체 발송은 회수할 수 없다.
- 중단 전 `pending`은 재활성화 시 처리된다. 오래된 알림을 보내지 않을 경우 운영자가 해당 범위를 확인해 `skipped`로 종료한 뒤 재활성화한다. 꺼진 동안의 사건은 소급 적재하지 않는다.
- 이전 앱으로 롤백할 때 새 테이블·컬럼은 유지한다. 데이터 삭제 DDL은 필요 없다.
