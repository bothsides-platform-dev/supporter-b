# 로그인 전 견적 Slack 행동 스레드

## 동작과 경계

두 기능 플래그가 켜진 뒤 새로 시작한 초안만 적용한다. 기존 `guest_rfp_events`가 있는 초안은 소급 생성하지 않는다. 첫 홈페이지 입력의 작성 시작을 Bot 원문 한 개로 보내고, `channel`·`ts`를 `guest_journeys`에 보관한다. 첫 댓글은 분석 링크이며 늦은 식별자·새 세션은 같은 댓글을 `chat.update`로 갱신한다. 작성 완료·질문·가입 선택·복귀·최종 요청 행동은 내부 DB에 보관하고 동일 스레드에는 10분 요약만 보낸다. 채널 재방송은 하지 않는다. 다른 운영 알림은 기존 Incoming Webhook을 쓴다.

`funnel-definitions.ts`의 단계·이벤트 정의를 재사용한다. `funnel.ts`가 정제한 행동을 GA와 내부 수집기에 독립 전달하며, GA 미설정·차단이 내부 수집을 막지 않는다. `journey-contract.ts`는 이벤트 UUID·정의된 단계·관측 시각·고정 오류 코드·선택 분석 ID와 허용된 완료 단계의 제한된 답변을 허용한다. 2026-10-24 사용자 결정에 따라 질문 완료 시 해당 답변과 가입 단계 완료 시 이메일·회사명·사업자등록번호·담당자명·인증된 연락처를 Slack 전용 `answer`로 기록한다. GA에는 전달하지 않는다. 완료/수정 시점의 값을 최대 500자로 보관하며 초과분은 말줄임표로 표시한다. 빈 답변은 미입력, 첨부는 개수만 표시한다. 개별 키 입력·비밀번호·인증번호·인증 ID·파일명·원본은 포함하지 않는다. 노출·오류·건너뛰기에는 답변을 붙이지 않는다. 자유 입력의 Slack 제어 문자를 escape하고 줄바꿈을 구분자로 표시한다. 이미 기록된 행동의 답변은 소급 복구하지 않는다. 반복 오류·재시도는 별도 이벤트 ID로 보존한다. 가입 완료와 요청 성공은 업무 트랜잭션의 savepoint에서 서버가 단 한 번 기록한다. 심사 대기·복귀는 화면 관측이며 관리자 승인 시각을 뜻하지 않는다.

익명 수집은 서버 발급 HttpOnly 초안 증명의 SHA-256과 대조한다. 기존 회원 로그인 연결은 같은 증명과 현재 active·이메일 인증 구매사 멤버십을 함께 요구한다. 가입 트랜잭션으로 이미 연결된 사용자는 미인증·심사 대기 중에도 자기 초안의 행동을 기록한다. 이후 요청은 DB 소유 사용자·워크스페이스와 클라이언트가 고정한 expected owner 모두 일치해야 한다. 다른 기기 복원도 이 소유권으로 같은 스레드에 연결한다. PG·운영계정·철회 세션·비활성 계정은 거부한다. 로그아웃/계정·워크스페이스 변경 시 브라우저 연결을 지운다.

증명 발급 응답을 받은 뒤에만 작성 시작을 등록한다. 행동 수집과 가입 저장의 증명 발급은 같은 브라우저 큐를 공유하며, Web Locks 지원 브라우저에서는 탭 사이에도 직렬화한다. 늦게 도착한 `Set-Cookie`가 이미 저장한 초안의 증명을 교체하는 경합을 막는다. 회원 초안의 임시 저장은 최종 요청 성공으로 기록하지 않는다.

## 수집·배치·장애

새 탭에서 익명 초안을 복원하면 HttpOnly 증명으로 기존 여정만 재연결한다. 이 복원은 새 원문을 만들거나 과거 초안을 소급 등록하지 않는다. 브라우저는 sessionStorage에 최대 100개 행동을 두고 15초·페이지 이탈 때 최대 10개씩 전송하되 답변을 포함한 UTF-8 요청이 4KiB를 넘지 않도록 더 작은 묶음으로 나눈다. SDK 식별자는 60초마다 다시 관측하며 각 SDK 대기는 최대 1.5초다. 요청 완료 후 새 수집은 멈추고 이미 쌓인 행동은 백그라운드에서 전송한다. 서버는 완료 후 최대 24시간 동안 이미 관측한 행동의 지연 도착을 받지만 직접 삭제한 초안은 즉시 차단한다. 네트워크·브라우저 종료·저장소 차단·100개 초과 시 유실될 수 있으므로 업무 감사 로그를 대체하지 않는다.

로그인 연결이 429·네트워크 오류로 실패하면 연결할 소유자를 sessionStorage에 보관하고 다음 전송 주기에 연결부터 재시도한다. 연결이 확인되기 전에는 익명 행동을 로그인 세션으로 보내지 않는다. 자동화처럼 질문 전체를 몇 초 안에 완료하면 10개씩 나누는 전송 때문에 마지막 행동 수집까지 수 분 걸릴 수 있다.

기존 Origin/ingress Host 검사, 4KiB·3초 body cap, IP당 10회/분·전체 60회/분 제한을 유지한다. 추가로 시작은 하루 전체 1,000개·증명당 익명 초안 5개, 초안당 보관 행동 5,000개·분석 세션 50개를 제한한다. 관측 시각은 과거 24시간~미래 5분만 허용한다. 클라이언트 시각과 분석 ID는 비신뢰 관측값이다.

기존 1분 `flush-outbox` cron은 유지한다. 초안 생성 후 10분, 이후 직전 행동 배치의 생성/마지막 선점 시각 중 늦은 시각으로부터 10분이 지나고 새 행동이 있을 때만 한 번 요약한다. 과거 분별·10개별 분할은 제거하여 적체된 행동도 요약 하나로 합친다. 요약에는 마지막 관측 단계, 주요 완료 단계, 최근 답변 최대 4개(각 100자), 오류별 횟수 최대 5개와 관리자 여정 상세 링크를 넣는다. 전체 답변·반복 오류·화면 이동은 DB에 그대로 남긴다. 서버 요청 완료는 대기 주기를 건너뛰고 다음 cron에서 남은 행동과 함께 한 번 요약한다. 완료 배치에 연결한 뒤 늦게 수집한 행동은 관리자 상세에서만 조회하며 새 Slack 댓글로 보내지 않는다. 완료 배치의 전송이 미확정이어도 자동 재발송하지 않는다. DB advisory lock·원자 claim·단일 gate로 cron 중첩과 HTTP 즉시 발송을 직렬화하고 Slack 호출 사이를 최소 1.1초 띄운다. 요청당 최대 20건으로 제한하므로 적체 시 지연될 수 있다. 시작 요청은 즉시 한 건을 시도하고 나머지는 cron이 처리한다.

- `pending`: 아직 보내지 않았거나 확실한 429. `Retry-After` 이후에만 재시도한다.
- `inflight`: 발송을 선점했다. 60초가 지난 상태는 `unknown`으로 전환한다.
- `sent`: Slack 응답의 `channel`·`ts`까지 저장했다.
- `unknown`: timeout·5xx·불완전 응답·프로세스 종료 등 도착 여부 미확정. 자동 재발송하지 않는다.
- `failed`: 명시적 거절/설정 오류. 자동 재발송하지 않는다.

`guest_journey.delivery`·`abandoned_claim`·`collect_failed`·`lifecycle_failed`·`flush_failed` 로그를 확인한다. 원문·토큰·분석 ID는 오류 로그에 넣지 않는다. root 또는 첫 분석 댓글이 미확정이면 하위 댓글도 보내지 않는다. 운영자는 Slack에서 실제 도착 여부를 먼저 확인한다. 미확정 행을 삭제하거나 무조건 pending으로 바꾸면 중복될 수 있다. 정확히 한 번 도착을 보장하지 않는다.

## 분석 보고서

GA 속성 `540469131`에 [로그인 전 견적 · Slack 사용자 탐색](https://analytics.google.com/analytics/web/#/analysis/a396924123p540469131/edit/cd9F5C6iTDSVJEFjjEWsWw)을 준비했다. Slack 댓글의 관측 날짜로 보고서 기간을 맞추고 `client_id` 또는 로그인 후 서버 확인 `User-ID`를 조회한다. `session_id`도 함께 제공한다. 보고서는 500행 표시로 준비했으며 기간을 좁힌 뒤 유효 사용자 ID 열에서 식별자를 찾고 해당 행을 눌러 타임라인을 연다. 개별 사용자 URL을 조합하지 않는다. 탐색 보고서는 생성 계정 소유이므로 다른 운영자가 필요하면 GA 안에서 보고서를 공유하고 속성 접근 권한을 확인한다.

GA 식별자는 공식 `gtag('get', measurementId, 'client_id'|'session_id', callback)`으로 받는다. 미확보는 명시한다. Clarity는 고정 프로젝트 `xiq81e87yn`의 player 링크와 `guest_rfp_draft` 태그를 유지한다. 링크 확보는 재생 가능성의 증명이 아니며 댓글에도 이를 구분한다. 제보 링크는 사전 조사에서 재생됐지만 간헐적 미노출 원인은 미확정이다.

## 보존·탈퇴

행동·분석 ID·발송 본문은 30일 보관한다. 완료/삭제된 연결과 익명 연결은 각각 종결/생성 후 30일에 제거한다. 미완료 회원 연결은 초안 수명 동안 남기고 오래된 행동·분석 ID와 본문만 정리한다. 원문/분석 발송 상태는 중복 방지 tombstone으로 남긴다. 계정 탈퇴는 관련 내부 연결·행동·배치를 cascade 삭제한다. 이 정책은 내부 DB 보존이며 이미 보낸 Slack 메시지와 GA/Clarity 보존은 해당 서비스 정책을 따른다. 보관 기간 정리는 행 잠금 후 현재 소유권·분석 목록으로 판단해 동시 가입이나 새 세션 추가 결과를 덮어쓰지 않는다. 플래그를 명시적으로 `false`로 내려도 기존 연결의 가입 소유권·요청 완료/삭제 처리와 cron 정리는 계속된다. 새 초안을 등록하거나 Slack에 발송하지는 않는다.

## 배포·롤백 순서

Bot 토큰 발급: [Slack 앱 관리](https://api.slack.com/apps)에서 기존 알림 앱을 선택하거나 앱을 만든다. **OAuth & Permissions → Bot Token Scopes**에 `chat:write`를 추가하고 **Install to Workspace / Reinstall to Workspace**로 설치한다. 같은 화면의 **Bot User OAuth Token**(`xoxb-` 접두어)을 서버 비밀 설정에 보관한다. `#prod-noti`의 채널 정보 → 통합 → 앱 추가에서 해당 앱을 참여시킨다. 토큰 자체를 채팅이나 Git에 남기지 않는다. [Slack 토큰 문서](https://docs.slack.dev/authentication/tokens/).

1. 앱 배포 전에 `scripts/migrations/20261020-guest-journey.sql`을 적용한다. 네 테이블과 CHECK/PK/인덱스, `guest_journey_gate`의 `id=1` 행을 확인한다. 기존 업무 행은 변경하지 않는다.
2. 서버 비밀 설정에 `SLACK_BOT_TOKEN`을 넣는다. Bot 권한은 `chat:write`이며 대상 `#prod-noti` 채널(`C0BTGP7HY6P`)에 참여해야 한다. `SLACK_GUEST_CHANNEL_ID`와 위 보고서 URL의 `GA_GUEST_EXPLORATION_URL`을 설정한다. 보고서 URL은 `#`를 포함하므로 `.env.production`에서 반드시 큰따옴표로 감싼다. 기존 웹훅은 유지한다.
3. 서버 `GUEST_RFP_SLACK_THREADS_ENABLED=true`, 빌드 `NEXT_PUBLIC_GUEST_RFP_SLACK_THREADS_ENABLED=true`를 함께 설정하고 정상 배포 경로로 빌드·재시작한다. 비밀 토큰은 `NEXT_PUBLIC_*`에 절대 넣지 않는다.
4. 새 테스트 초안을 시작해 원문 1개, 분석 첫 댓글, 생성 후 10분이 지난 cron의 진행 요약, 늦은 SDK 분석 갱신을 확인한다. 최종 요청 완료 요약은 10분 대기 없이 다음 cron에서 한 번 전송되는지 확인한다. 가입·인증·복귀·명시적 요청 후 서버 성공 이벤트가 한 번씩인지 확인한다. 이 smoke는 실제 Slack 알림을 만든다.
5. 롤백은 두 플래그를 `false`로 내리고 재빌드·재시작한다. 새 초안은 기존 웹훅 방식으로 돌아가고 이미 스레드가 있는 초안은 구 클라이언트의 채널 중복 알림을 억제한다. 테이블·원문 발송 상태를 삭제하지 않는다. cron은 유지한다.

2026-10-20 적용 기록: 운영 DB에 전용 DDL을 단일 트랜잭션으로 적용했다. 네 테이블·소유권/상태 CHECK·외래키·gate 1행을 확인했으며 업무 데이터 변경이나 과거 초안 백필은 없다. GA 탐색 보고서도 생성했다. 운영 서버에는 기존 웹훅만 있고 Bot 토큰은 없어서 앱 배포·기능 활성화·실제 Bot 발송은 아직 실행하지 않았다.

검증: 전체 단위 테스트 8,902개 통과 후 로그아웃 쿠키 회귀를 추가하고 관련 25개 테스트를 통과했다. 타입 검사·lint·`next build --webpack`도 통과했다. 실제 Postgres의 격리 스키마에서 DDL·원문/댓글/갱신·분 묶음·Retry-After를 확인했다. 운영용 빌드의 Playwright 5개 시나리오가 통과했다: 기존 회원 로그인→최종 요청, 신규/갱신 가입→인증·심사 대기→다른 기기 복원→최종 요청, PG 계정 차단, 로그아웃→다른 구매사 로그인 후 기존 증명 재사용 차단. 자동화 사용자는 Caddy의 IP 헤더를 각각 분리했고, 빠른 질문 완주로 쌓인 행동은 실제 15초 전송 주기를 기다려 검증했다. SQL 날짜 인자·증명 발급 경합·캐시 세션 재적용·연결 429 재시도·임시 저장의 성공 오기록을 수정했다. 또한 Next.js가 `Max-Age=0`을 생략하는 쿠키 왕복을 재현해 로그아웃 쿠키에 명시적 과거 만료일을 추가했다. 브라우저 검증은 Slack 실발송 없이 수행했다.
