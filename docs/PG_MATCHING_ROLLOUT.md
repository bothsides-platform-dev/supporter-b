# 맞춤 PG 상담 적용

## 제품 결정

2026-09-19 사용자 확인: 실제 구매사 흐름 및 PG 심사·거절·다음 추천을 적용한다. 운영표는 관리자 설정으로 관리한다. **상담 요청 → PG 심사·견적 → 구매사 최종 선정**이며 선정 시 기존 전자서명 준비가 시작된다.

`/tmp/supporter-b-buyer-demo-followup-20260919.md`의 랜딩·튜토리얼 후속 작업은 별개다. 이번 변경은 샘플 위저드의 기존 동작을 유지한다.

## 배포 순서

1. 대상 DB와 백업을 확인하고 `scripts/sql/20260919-pg-matching.sql`의 추가 DDL을 적용한다. 세 테이블·인덱스와 `outbox_event` 값 하나만 추가하며 기존 견적·초대·업종 매핑을 수정하지 않는다. 이미 같은 이름의 객체가 있다면 정의가 일치하는지도 확인한다. 스크립트는 자체적으로 `ON_ERROR_STOP` 을 켜고 테이블·인덱스 생성을 한 트랜잭션(`lock_timeout 5s` · `statement_timeout 30s`)으로 묶으므로, 중간에 실패하거나 잠금을 기다리다 끊기면 반쪽 스키마가 남지 않고 통째로 롤백된다. `outbox_event` 값 추가(`ALTER TYPE … ADD VALUE`)만은 트랜잭션 밖에서 먼저 실행된다 — Postgres 가 트랜잭션 안의 enum 값 추가를 허용하지 않기 때문이며, 이 한 줄은 멱등(`IF NOT EXISTS`)이라 재실행해도 안전하다.
2. admin-supporter-b의 대응 브랜치를 배포한다. `/pg-recommendations`에서 업종별 접수 분류, PG 추천 순서, 사유, 확인된 영세 요율 범위와 적용 조건을 등록한다. 업종별 후보가 없으면 아래 기본 추천 설정을 사용한다. 기존 연결을 자동으로 White로 승격하지 않는다.
3. supporter-b 대응 브랜치를 배포한다. 신규 상담에는 업종과 제출 키가 필수다. 이전 브라우저 탭은 새로고침 안내를 받으며 신규 화면에서 다시 진행한다.
4. 테스트 계정으로 상담 요청, PG 검토·거절, 다음 추천·새 마감, 견적 제출, 구매사 최종 선정까지 확인한다. 선정 이전에는 `signing_contracts`가 생기지 않아야 한다. 거절한 PG에게 다음 후보나 다른 PG의 이력이 보이지 않아야 한다.

본 작업은 로컬 구현이며 운영 DDL·설정 입력·배포를 실행하지 않았다.

## 운영 설정

- White: 일반 업종. Gray: 추가 검토. Black: 접수 불가. 정책이 없거나 유효하지 않으면 미설정으로 처리한다.
- 동일 PG의 여러 업종 등록이 가능하다. 승인된(active) PG만 추천하며 테스트 PG는 기존 표시 쿠키를 따른다.
- 등록된 순서대로 제안한다. 이전에 상담한 PG는 제외한다. 수용 가능성을 회사명으로 추정하지 않는다.
- PG별 요율은 양 끝을 모두 비우거나, 최저≤최고 범위와 적용 조건을 함께 입력한다. 미입력 시 견적에서 안내한다.
- 전송 키는 입력 내용의 해시와 함께 저장한다. 응답을 받지 못한 동일 요청의 재시도는 같은 견적 번호를 돌려주고, 내용을 수정한 재시도는 성공으로 오인하지 않도록 중단한다.
- 업종을 삭제하면 진행 중인 요청의 스냅샷은 남지만 다음 자동 추천은 중단된다. 문의 주소는 기존 운영팀 `help@support-b.com`이다.
- 거절·철회는 앱 알림과 이메일을 보낸다. 연락 소요 시간 안내는 영업일 1~5일이며 자동 승인이나 자동 최종 선정이 아니다.

영세/신규 환급 문구 근거: [금융위원회 2026년 하반기 우대수수료 안내](https://www.fsc.go.kr/no010101/87498). 연 매출 3억 원 이하, 반기별 선정·차액 환급 안내이며 정확히 6개월 후 자동 전환이나 모든 PG의 0.8~0.9%를 보장하지 않는다.

## 복구

접수를 막아야 하는 업종은 관리자에서 Black(접수 불가)으로 전환한다. 미설정은 기본 추천 PG를 사용하므로 차단 수단이 아니다. 진행 중인 상담과 이력은 유지한다. 앱을 이전 코드로 되돌리면 새 상담의 단일 PG 제약을 이전 코드가 알지 못하므로 **단순 앱 롤백은 호환되지 않는다**. 새 상담 쓰기를 일시 중단한 뒤 이 브랜치로 복구하는 방식으로 운영한다. 추가 테이블을 삭제해 이력을 잃는 롤백은 하지 않는다.

## 2026-09-24 업종 선택·기본 추천 적용

1. 양쪽 앱 배포 전에 `scripts/sql/20260924-pg-matching-defaults.sql`을 대상 DB에 적용한다. 기존 업종에 nullable MCC 코드·판본과 코드 UNIQUE를 추가하고 기본 추천 싱글턴 테이블을 만든다. 기존 데이터는 변경하지 않는다. 같은 이름의 기존 DB 객체가 있으면 정의 일치도 확인한다.
2. 관리자 앱을 배포하고 `/pg-recommendations`의 **기본 추천 PG**에서 활성 PG 한 곳 이상과 추천 사유를 저장한다. 순서와 요율 조건은 업종별 정책과 같은 방식으로 편집한다.
3. **표준 업종에서 선택**에서 업종을 검색·복수 선택해 등록한다. 카탈로그는 Visa 2026년 4월 MCC 중 상담에 쓸 29개를 번역한 목록이며 전체 표준 목록이나 실제 가맹점 MCC 확정을 대신하지 않는다. 출처·코드·판본은 관리자 `lib/mcc-catalog.ts`가 소유하고 DB에 코드·판본을 보존한다. 코드 또는 이름이 이미 있으면 기존 ID·PG 매핑·정책을 보존하고 건너뛴다.
4. 구매사 앱을 배포한다. 구매사는 업종 이름을 직접 선택하고 내부 UUID를 초안에 저장한다. 업종 목록이 없으면 건너뛰지 않고 재조회할 수 있다.
5. 업종별 유효 후보가 없으면 기본 후보를 Gray로 제안한다. 서버 제출과 다음 PG 추천도 같은 규칙을 재검증한다. Black, 존재하지 않는 업종, 비활성 PG, 이전 상담 PG는 우회하지 않는다. 기본 후보가 전부 소진되거나 기본 설정이 없으면 운영 설정 보완이 필요하다.

기본 후보의 지정은 운영자가 결정한다. DDL만 적용해서는 실제 PG나 업종이 자동 등록되지 않는다. 되돌릴 때 추가 컬럼·테이블을 삭제하지 않는다. 이전 코드로 돌아가면 기본 추천이 사라져 미설정 업종의 접수가 다시 막힐 수 있다.

검증: 추천 저장소의 fallback/차단/후보 소진 테스트, 실제 상담 액션의 기본 PG 제출·Gray 스냅샷·심사 이력 저장 테스트, 관리자 권한·일괄 등록 중복 보존 테스트, 추가 DDL 재실행·기존 행 보존·제약 테스트를 포함한다. 운영 DDL·설정 저장·배포는 실행하지 않았다.
