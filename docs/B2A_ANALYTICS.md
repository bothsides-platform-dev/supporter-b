# B2A 애널리틱스

2026-11-09 · v0.50.0.0 (분석 수집은 v0.49.0.0). 현재 브랜치와 최신 `origin/dev`의 기존 GA4·Clarity·Axiom·guest journey 구조를 확인하고 확장했다. 운영 설정 변경이나 배포 완료를 뜻하지 않는다.

## 기존 분석과 연결

| 경로 | 기록하는 사실 | 쓰임 |
|---|---|---|
| 기존 GA4 구매사 퍼널 | `agent` 단계의 동의 화면·승인/거절 클릭·상담 확인·발송 시도·발송 후 화면·연결 관리 화면 | 브라우저에서의 행동. 서버 전환과 더해서 집계하지 않음 |
| 기존 Axiom/Pino | `agent.analytics`: 정해진 채널·작업·결과·오류 코드·시간·준비 규칙 | CLI를 포함한 호출 진단. `agent.discovery`는 이전 공개 조회 로그로 유지하며 두 이벤트를 합쳐 호출 수를 세지 않음 |
| Postgres `agent_events` | 동의·최초 토큰 발급·갱신·초안·실제 상담 발송·철회 | 업무 변경과 같은 트랜잭션에 저장하는 전환 원장 |
| Postgres `agent_observations` | 공개/계정 API 호출 결과와 처리 시간, 검증한 연결과 요청, 신규/변경·준비 규칙 | 실패·준비 상태 분석. 선택적 수집이며 누락 가능 |

GA4의 기존 구매사·운영계정 구분, 운영 환경 전송, 고정 이벤트·단계·경로 allowlist를 재사용한다. CLI 호출을 브라우저 방문이나 GA 사용자로 만들지 않는다. `submitted_view`는 발송된 상담을 본 사실이며 신규 발송 성공 사건이 아니다. GA4 맞춤 측정기준은 기존 `funnel_id`, `step_id` 등을 그대로 쓴다.

`connected`는 동의 후 인증 코드를 발급한 시점이다. `token_issued`는 최초 코드 교환 성공이며 같은 연결의 갱신은 `token_refreshed`다. 토큰 발급도 클라이언트가 응답을 받았다는 증명은 아니다. 실제 도구 사용은 별도 호출 관측으로 확인한다. 과거 동의만 있는 데이터를 인증 성공으로 백필하지 않는다.

OAuth 코드·state·PKCE·토큰·원본 URL/쿼리·헤더·클라이언트 앱 이름·대화·자유 입력·업체 이름·금액·연락처는 새 관측에 넣지 않는다. 누락은 `website-required`, `pg` 같은 규칙 이름만 받는다. 서버가 검증한 연결·요청 ID는 내부 DB에만 저장하고 Axiom에는 보내지 않는다. 이 DB 기록은 연결을 통해 사용자와 결합되므로 익명 자료가 아니다. 공개 호출을 기존 브라우저 쿠키나 최초 유입 기록과 임의로 연결하지 않는다.

현재 관측만으로 알 수 없는 값은 추천 노출·고유 익명 사용자·검증된 하네스·미지원 분야 수요다. 제휴사 계약·연동·수수료는 별도 [확인 원장](B2A_OUTCOMES.md)으로 연결하며 호출 관측에서 추정하지 않는다. 리포트의 `unmeasured`로 표시하며 0건으로 오해하지 않게 한다. 신규/변경과 준비 항목은 이미 검증한 도구 결과에서만 얻는다. 외부에서 입력한 하네스 이름을 실제 사용 실적으로 확정하지 않는다.

## 집계 기준

- 연결 전환: 기간 내 `connected`가 기록된 **연결**을 기준으로, 종료 시각 전 토큰 발급·도구 사용 관측·초안·발송을 확인한다. 여러 이벤트가 있어도 연결별 한 번이다. 재연결은 별도 연결이며 고유 고객 수가 아니다.
- 요청 전환: 기간 내 `draft_created`가 기록된 **요청**을 기준으로 종료 시각 전 발송 여부를 집계한다. 반복 저장·발송 재시도는 중복 신청으로 세지 않는다. 아직 발송되지 않았거나 종료 이후 발송한 요청은 `pending`이다.
- 호출: 개별 HTTP 요청 결과다. MCP의 HTTP 200 안에 있는 `isError`·프로토콜 오류도 실패다. timeout 뒤 늦게 끝난 업무의 원장과 호출 timeout은 서로 다른 사실이며 호출 관측은 한 번만 기록한다.
- 기간은 `[from, to)`다. 일별 날짜는 `Asia/Seoul`로 구분한다. 환경별로 분리하며 `NODE_ENV=production`만으로 운영 실적으로 추정하지 않는다.
- 호출 원본은 30일 보관하며 제한·장애·정리 때문에 누락될 수 있다. 전환 원장과 호출 이용 관측의 수집 범위는 다르다. 빈 리포트가 실제 이용 0건을 증명하지 않는다.

## 조회

관리자 웹은 별도 `admin-supporter-b` 저장소다. 이 저장소에는 공개 분석 API나 고객용 전체 집계 화면을 추가하지 않는다. 여기서는 운영자 서버의 DB 접근 권한으로 집계만 조회한다. 관리자 웹 연결 시 기존 `data.view` 권한을 조회 전에 검사해야 한다.

`DATABASE_URL`을 주입한 운영자 셸에서 실행한다. CLI는 환경 파일을 자동으로 읽지 않고 인증정보를 출력하지 않는다. 날짜만 입력하면 한국 시간 자정이며 `--to`는 제외한다. 기본값은 최근 28일·`production`이다. 한 번에 최대 93일을 조회한다.

```sh
pnpm b2a:analytics report --from 2026-11-01 --to 2026-11-09
pnpm b2a:analytics report --environment production --format json --output /tmp/b2a-report.json
pnpm b2a:analytics report --environment staging --format html --output /tmp/b2a-report.html
```

HTML은 브라우저에서 열 수 있는 독립 리포트다. 외부 스크립트·추적기·고객 식별자·상담 원문을 포함하지 않는다. 연결 전환, 준비 중 요청, 날짜/기능별 호출·실패·평균/P95, 준비 항목, 계약·연동 확인과 통화별 수수료 확정·지급·잔액을 제공한다. 리포트는 생성 시점의 스냅샷이며 실시간 관리자 대시보드는 후속 연결 작업이다. 장기 추세가 필요하면 원본 정리 전에 월별 리포트를 운영 보관소에 내보낸다. 자동 월별 보관 스케줄은 이번 로컬 구현에서 등록하지 않았다.

## 배포와 정리

1. 기존 계정 채널 DDL 이후 [20261108-agent-analytics.sql](../scripts/migrations/20261108-agent-analytics.sql)을 앱 배포보다 먼저 한 번 적용한다. 관측 테이블·인덱스와 업무 이벤트의 환경 열을 추가하며 기존 행은 `unknown`으로 남는다. v0.50.0.0에서는 이어서 [20261109-partner-outcomes.sql](../scripts/migrations/20261109-partner-outcomes.sql)도 앱 배포 전에 적용한다.
2. `AGENT_ANALYTICS_ENVIRONMENT=staging` 등 환경을 명시하고 앱을 배포한다. 운영은 `production`, 테스트는 `test`다. 미설정 production 런타임은 `unknown`이며 개발·단위 테스트 런타임은 해당 분류를 기본으로 쓴다.
3. `AGENT_ANALYTICS_ENABLED=true`로 선택 관측의 DB 저장을 활성화한다. 기본 false에서는 Axiom/표준 로그만 남고 추가 관측 DB 접근은 없다. 업무 원장 기록은 이 플래그와 독립이다.
4. 스테이징에서 동의만 한 연결·토큰 교환 성공·누락 초안·발송·잘못된 입력·권한 실패를 실행하고 `--environment staging` 리포트와 DB를 대조한다. GA4는 기존 운영 전송 조건을 유지하므로 운영 DebugView 확인은 별도다.
5. 관측 정리를 기존 운영 스케줄러에 연결한다. 먼저 미리보기로 대상을 확인하며 실행당 최대 5,000건이다. 남은 건이 있으면 다음 배치에서 계속 처리한다.

```sh
pnpm b2a:analytics prune
pnpm b2a:analytics prune --execute
```

정리는 30일 지난 호출 관측만 삭제한다. 상담·초안·연결·토큰·업무 전환 원장은 삭제하지 않는다. 회원·연결·요청 물리 삭제는 FK cascade로 연결된 관측도 삭제한다. 앱 롤백은 수집을 끄고 이전 앱으로 되돌리되 새 테이블과 기록은 보존한다.

관측은 프로세스당 분당 2,400건, DB 동시 저장 8개로 제한한다. DB 문장 제한 500ms·잠금 제한 200ms, 호출자 대기 750ms를 적용한다. 시간이 지나도 진행 중인 저장은 슬롯을 차지하며 자동 재시도하지 않는다. 저장 실패·대기 초과에는 30초 동안 DB 수집을 쉬고, 생략 이유만 분당 한 번 경고한다. 이러한 누락을 가짜 성공이나 실패 행으로 메우지 않는다. 관측 장애는 기존 업무 성공을 취소하지 않는다.

## 계약·수수료 연결과 후속 작업

**2순위였던 계약·수수료 결과 연결을 구현했다.** [운영 절차와 집계 정의](B2A_OUTCOMES.md)에 따라 확인 주체·출처·발생/기록 시각·정정 이력을 보관한다. 노온 합의서와 PG 서비스 계약을 구분하며 미입력 결과를 추정하지 않는다. 원장은 요청 생성 기간·원래 환경을 기준으로 집계하고 종료 시각 전 발생·기록된 사실만 포함한다. OAuth 물리 삭제 후에도 거래 원장은 보존되므로 사라진 연결 집계와 단순히 나누어 전환율을 계산하지 않는다.

운영 반영·실제 제휴사 근거 입력·관리자 웹·발견 경로·SDK 작업은 사용자와의 후속 대화에서 진행한다.

## 로컬 검증 기록

- 관련 27개 파일·248개 테스트, 전체 타입 검사, 변경 코드 ESLint·diff 검사·비밀값 검사 통과. Clarity의 예약된 SDK 재시작 경계를 보완한 뒤 관련 4개 파일·32개 테스트를 추가로 확인했다.
- 운영과 분리된 Postgres에서 실제 추가 DDL 적용, 시험 관측 2건 저장, CLI HTML 생성, production 리포트의 시험 데이터 제외를 확인했다. 기존 시험 상담 2건은 보존했다.
- Chromium 1280px·390px에서 독립 리포트와 실제 동의/확인/누락 컴포넌트의 표시를 확인했다. OAuth 직접 진입의 SDK 미로드와 일반 SPA에서 인증 화면으로 갈 때 전체 문서 이동도 검증했다. 외부 분석 요청은 테스트 응답으로 대체했다.
- 운영 DDL·배포·GA4 DebugView 실수신·Axiom 원격 수신·관리자 웹 대시보드 연결·정리 스케줄 등록은 수행하지 않았다. 이번 검증이 실제 이용 지표 수집을 증명하지 않는다.
