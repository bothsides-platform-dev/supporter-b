# PG 여정 UI/UX 재설계 — 설계 문서

- **작성일**: 2026-06-06
- **범위**: PG(결제대행사 영업담당) 워크스페이스 여정 — `참여 가능한 견적` → `수신함` → `견적 작성` → `견적 보냄`
- **상위 목표**: "한 화면에서는 하나의 정보(또는 행동)만 강조"하여 사용자가 무엇을 할지 헷갈리지 않게 한다. 업계 표준 패턴을 따른다.
- **비범위**: 구매사 여정(생성→상세→선정)은 별도 spec(#2)에서 다룬다. 본 문서는 PG 측만.

> 본 문서는 브레인스토밍에서 사용자가 화면별로 승인한 결정을 기록한 것이다. 구현 계획은 후속 writing-plans 단계에서 생성한다.

## 1. 북극성 원칙 — "하나만 강조"의 정의

화면 아키타입마다 '강조할 단 하나'를 다음과 같이 고정한다. 모든 화면 설계는 이 표를 따른다.

| 아키타입 | 화면 | 강조할 단 하나 | 강등(demote) 대상 |
|---|---|---|---|
| 목록 | 참여 가능한 견적 / 수신함 | "지금 행동할 대상 + 급한 정도" (구매사·마감임박·신규) | 견적번호·홈페이지·등급 등 부가정보 → peek/펼침 |
| 작성(폼) | 견적 작성 | "지금 단계의 입력 그룹 하나" (위저드 1단계=1태스크) | 다른 단계, 템플릿/초안 관리 도구 |
| 완료 | 견적 보냄 | "안심 메시지 1개 + 다음 행동 1개" | 견적 요약 → 기본 접힘 |

**전 화면 공통 신호 통일**
- **마감 임박**: 빨강 `D-n` 칩(D-2 이하 빨강, 그 이상 중립). 모든 PG 화면에서 동일한 시각 신호.
- **1차 CTA는 화면/행마다 하나**. 보조 행동은 ghost/text 버튼으로 시각적 강등.

## 2. 핵심 결정: 견적 작성은 **단계형 위저드** (가장 큰 변경)

현재 `BidForm`(592줄)은 한 좁은 컬럼에 정산조건 + 수수료(동적 4~9칸) + 견적서 + 템플릿 + 초안복구 + 검증메시지 4종 + 발송 CTA가 모두 경쟁한다. 이를 **단계형 위저드**로 전환한다.

선정 이유:
- '하나만 강조'를 구조적으로 강제(한 단계 = 한 입력 그룹).
- 구매사 RFP 작성 위저드(`RfpCreateWizard`)와 **대칭** → 양측 사용자가 동일 멘탈모델.

### 2.1 단계 구성 (4단계)

| 단계 | 제목 | 내용(현 BidForm 매핑) | 1차 CTA |
|---|---|---|---|
| 1 | 정산 조건 | 정산주기, 정산한도, 월보증보험 | 수수료 → |
| 2 | 수수료 | 요청된 결제수단별 수수료율(동적 4~9칸) | 견적서 → |
| 3 | 견적서 | 견적서 PDF 업로드 + 메모 (선택) | 검토·발송 → |
| 4 | 검토·발송 | 전 단계 요약 + 비가역 경고 + 발송 | 견적 보내기 |

### 2.2 파워유저 보호 (위저드의 속도 저하 방지)

PG는 견적을 **반복 제출하는 영업담당(파워유저)**이다. 위저드가 속도를 깎지 않도록 — 구매사 위저드와 동일하게:

- **단계 자유 점프**: 사이드바에서 아무 단계나 클릭 이동(순차 강제 금지).
- **키보드 이동** 유지.
- **초안 자동저장**이 단계 전환 후에도 유지. 사이드바에 `💾 자동저장됨 · HH:MM` 표시.
- **템플릿 불러오기 = 1단계 진입 장치**: 한 번에 전 단계를 일괄 채움.

### 2.3 밀집 요소 5종 배치 (확정)

| 요소 | 배치 |
|---|---|
| 템플릿 불러오기 | 1단계 진입 시 버튼(전 단계 일괄 채움) |
| 템플릿으로 저장 | 4단계(검토·발송)에서만 노출 — 체크박스 |
| 초안 복구 배너 | 위저드 진입(1단계) 1회만. 이후 단계는 '자동저장' 표시만 |
| 수수료 4~9칸 | 전용 2단계. **요청된 결제수단만** 카드 그리드(2열)로 스캔 쉽게 |
| 비가역 발송 경고 | 4단계에서 warning 박스로 **시각 지배** + 발송 시 확인 다이얼로그(현 `ConfirmDialog` 유지) |

### 2.4 구매사 컨텍스트 표시 — **얇은 상단 strip + 펼침** (승인안)

- 모든 단계 상단에 **한 줄 strip** 상시 노출: `구매사명 · 해당 단계의 요청 핵심`.
  - 예) 2단계에선 `요청: 카드·계좌이체·간편결제 수수료`.
- `요청 전문 ▾`으로 펼치면 구매사 브리프 전문(상호·등급·사업운영정보·메모·첨부).
- (대안이던 '왼쪽 고정 레일', '오버레이'는 미채택 — strip이 공간 최소·상시 노출.)

### 2.5 발송 후 상태

- 발송 완료 시 P4(견적 보냄) 화면으로 이동. 위저드는 1회 제출 후 재진입 시 읽기 전용/완료 상태로.

## 3. 목록 화면 정돈 (전면 재설계 아님 — polish-to-principle)

`참여 가능한 견적`·`수신함`은 현재도 비교적 깔끔하므로 구조는 유지하되 '하나만 강조' 원칙으로 정돈한다. 기존 `SplitView`(목록 + peek 패널) 패턴 유지.

### 3.1 P-opp · 참여 가능한 견적 (`/opportunities`)

- **강조**: "지금 잡을 만한가" — 구매사명·제목(1차 라인) + 마감 임박(빨강 D-n).
- 행 구성:
  - 1차 라인: `구매사명 · 제목`
  - 2차 라인: `결제수단 · 주요상품` (작게)
  - 우측: `D-n` 칩 + 단일 CTA `참여 요청`
- **강등**: 견적번호·홈페이지 링크 → 행에서 빼고 peek/펼침으로.
- 단일 행동: `참여 요청`(현 `OpportunityRequestDialog`).

### 3.2 P2 · 수신함 (`/inbox`)

- **강조**: "내가 응답해야 할 것 + 얼마나 급한가" — `신규` 칩 + 빨강 임박 D-n이 시각적으로 가장 강함.
- 행 구성:
  - 좌측: 상태 칩(`신규`는 강조색, 그 외 중립)
  - 1차 라인: `구매사명 · 제목`
  - 2차 라인(작게/muted): `견적번호 · 등급 [· 견적 보냄]`
  - 우측: `D-n` 칩 + 1차 행동
- **1차 행동(행당 하나)**: 상태별로 분기
  - `신규` → `견적 작성`(1차 CTA)
  - `견적 보냄` → `보낸 견적`(ghost, 조용한 보조)
- 기존 키보드 내비/필터/뷰토글은 유지.

---

## 4. 완료 화면 정돈 — P4 · 견적 보냄 (`/inbox/[rfpId]/submitted`)

- **강조**: 안심 메시지 1개 + 다음 행동 1개.
  - 큰 `✓` + `견적을 보냈어요` + 안내 한 줄(`구매사가 마감일까지 비교·검토 후 결과를 알려드려요`).
  - 다음 행동: `수신함으로`(1차) + `보낸 내용 보기 ▾`(보조).
- **강등**: 견적 요약(정산·수수료 등)은 **기본 접힘**, `보낸 내용 보기`로 펼침.

## 5. 디자인 시스템 정합

- Linear 디자인 하드룰 준수(`CLAUDE.md` / `DESIGN.md`): pill 버튼 금지(6px), 상태는 `Chip`, 저대비 보더, 14px 바디, 숫자 `.md-numeric`.
  - **예외 명시**: D-n 마감 칩과 P4의 `✓` 상태 배지는 status 지표이므로 `shape-full`(둥근 칩) 허용 — 이는 기존 status dot/pill 예외 범위.
- UX 라이팅은 `UX_WRITING.md`(토스 보이스톤) + §8 도메인 용어집('견적 요청'/'견적'/'선정') 준수. 코드 식별자·라우트·DB는 영어(RFP/bid) 유지.
- 화면/라우트 변경 없음(IA 동일) → `SCREEN_DESIGN.md` 라우트맵 변경 불필요. 단, P3가 폼→위저드로 바뀌므로 해당 스크린 표의 UX 스펙은 갱신한다.

## 7. 열린 항목 (구현 계획에서 결정)

- 위저드 단계 컴포넌트의 파일 경계 및 상태 호이스팅 위치.
- 좁은 화면(반응형)에서 상단 strip·사이드바의 접힘 규칙.
- '견적서(3단계)'의 선택 여부 — 메모/PDF 미입력 시 건너뛰기 허용 정책(현 검증: 정산주기+수수료 1개 이상이면 발송 가능)을 위저드 단계 이동 규칙에 어떻게 매핑할지.
