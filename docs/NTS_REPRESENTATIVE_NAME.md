# 사업자 대표자명 확보·검증 조사

조사일: 2026-09-13
범위: 대한민국 공식 1차 자료와 이 저장소의 현재 구현

## 결론

국세청의 `사업자등록정보 진위확인 및 상태조회 서비스`로는 **사업자등록번호만 보내
대표자명을 조회할 수 없다.** 현재 쓰는 `/status`는 사업 상태·과세유형·폐업일 등을
반환할 뿐 대표자명 필드가 없다. `/validate`의 대표자명(`p_nm`)은 응답으로 새로 얻는
값이 아니라 호출자가 이미 알고 제출해야 하는 필수 입력값이다.

서포트비에 적합한 경로는 다음과 같다.

1. 구매사에게 사업자등록증에 적힌 **대표자명과 개업연월일**을 입력받는다.
2. 서버가 `사업자등록번호 + 개업일자 + 대표자명`을 `/validate`에 보내 일치 여부를
   확인한다.
3. `valid === '01'`일 때만 검증된 대표자명으로 저장한다. 응답의
   `request_param.p_nm`을 조회 결과로 취급하면 안 된다. 그것은 요청값의 반향이다.
4. 개업일자는 재검증에 보관할 명확한 필요가 없다면 요청 순간에만 사용하고 저장하지
   않는다. 사업자등록증 파일도 OCR 보조가 꼭 필요하지 않다면 수집하지 않는 편이 낫다.

즉 UI 문구도 `대표자명 조회`가 아니라 `사업자 정보 확인` 또는 `대표자명 인증`이
정확하다.

## 국세청 API가 실제로 하는 일

공공데이터포털의 [공식 서비스 설명](https://www.data.go.kr/data/15081808/openapi.do)은
두 기능을 명시적으로 구분한다.

- 진위확인: 사업자등록번호, 개업일자, 대표자명 등을 **입력**하여 국세청 정보와
  일치하는지 확인한다.
- 상태조회: 사업자등록번호만으로 휴·폐업 상태, 과세유형, 폐업일자를 조회한다.

세부 계약은 공공데이터포털 페이지가 로드하는
[공식 Swagger/OpenAPI 명세](https://infuser.odcloud.kr/api/stages/28493/api-docs?1728017570963)에
있다.

| 구분 | `/status` 상태조회 | `/validate` 진위확인 |
|---|---|---|
| 목적 | 사업자 상태 조회 | 제출한 사업자 정보의 일치 여부 확인 |
| 필수 요청 | `b_no` | `b_no`, `start_dt`, `p_nm` |
| 대표자명 역할 | 없음 | `p_nm`(대표자성명1)이 필수 **입력** |
| 주요 응답 | `BusinessStatus`: 사업자번호, 납세자상태, 과세유형, 폐업일 등 | `BusinessValidation`: `valid`, `valid_msg`, `request_param`, `status` |
| 대표자명을 새로 반환하는가 | 아니오 | 아니오. `request_param`은 요청 스키마 `BusinessDescription`을 되돌린다. |

`/validate` 최소 요청 예시는 다음과 같다.

```json
{
  "businesses": [
    {
      "b_no": "3327800702",
      "start_dt": "YYYYMMDD",
      "p_nm": "사용자가 입력한 대표자명"
    }
  ]
}
```

명세상 모든 요청항목이 일치하면 `valid: '01'`과 상태조회 결과가 반환되고, 일치하지
않으면 `valid: '02'`, `valid_msg: '확인할 수 없습니다'`가 반환된다. 외국인 사업자는
`p_nm`에 영문명을 쓰며, `p_nm2`는 그 경우에만 한글명을 넣는 선택 항목이다. 명세는
`p_nm2`에 공동대표자명을 넣지 말라고 별도로 주의한다.

현재 코드는 [lib/integrations/nts.ts](../lib/integrations/nts.ts)에서 `/status`에
`{ b_no: [digits] }`만 보내고 `b_stt_cd`와 `tax_type`만 제품 값으로 매핑한다.
[BizProfile](../lib/types/biz-profile.ts)과
[biz_profiles 스키마](../lib/db/schema/biz-profiles.ts)에도 대표자명·개업일자가 없다.
따라서 현재 어댑터의 응답 파싱만 늘려서는 대표자명이 생기지 않는다.

## 가능한 확보 경로

### 1. 사용자 입력 후 국세청 진위확인 — 권장

가입 또는 설정의 사업자 프로필 폼에 대표자명과 개업연월일을 받고, 쓰기 경계에서
`/validate`를 호출한다. 사업자등록증 정식 서식에는 `대표자`와 `개업연월일`이 함께
기재된다. 근거는 국가법령정보센터의
[사업자등록증 법정 서식](https://law.go.kr/LSW/flDownload.do?flNm=%5B%EB%B3%84%EC%A7%80+%EC%A0%9C4%ED%98%B8%EC%84%9C%EC%8B%9D%5D+%EC%82%AC%EC%97%85%EC%9E%90%EB%93%B1%EB%A1%9D%EC%A6%9D%0A&flSeq=61511217)이다.

이 방식은 모든 국세청 등록 사업자에 같은 계약을 적용할 수 있고, 사용자가 적은 이름이
국세청 정보와 맞는지도 확인한다. 단, `valid: '01'`은 **제출 조합의 일치**를 뜻하지
대표자 본인의 계정 소유·재직 권한까지 증명하지는 않는다.

### 2. 사업자등록증 OCR 후 진위확인 — 입력 보조

사용자가 올린 사업자등록증에서 대표자명과 개업연월일을 OCR로 미리 채울 수 있다.
그러나 OCR은 오탈자가 가능한 입력 보조이고 국세청 조회가 아니다. 추출값을 사용자에게
확인시킨 뒤 같은 `/validate`에 보내야 한다.

파일 수집은 대표자명 직접 입력보다 더 많은 정보를 받는다. 대표자명 표시만 목적이라면
서류 원본을 영구 보관하지 않고 OCR 처리 후 즉시 폐기하는 설계가 최소수집 원칙에 더
가깝다. 실제 보관이 필요하면 그 목적·기간·접근권한을 별도로 정해야 한다.

### 3. OpenDART 기업개황 — 공시대상 법인에 한정된 보조 경로

금융감독원 OpenDART의
[기업개황 API](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019002)는
응답에 대표자명 `ceo_nm`과 사업자등록번호 `bizr_no`를 포함한다. 하지만 요청의 필수 키는
사업자등록번호가 아니라 공시대상회사의 8자리 `corp_code`다. 또한
[고유번호 파일 API](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019018)는
`corp_code`, 회사명, 영문명, 종목코드, 최종변경일만 제공하고 사업자등록번호는 제공하지
않는다.

따라서 이미 정확한 `corp_code`를 아는 공시대상 법인에는 보조 조회로 쓸 수 있지만,
사업자등록번호 하나로 모든 법인·개인사업자의 대표자명을 가져오는 범용 경로가 아니다.
회사명 검색으로 임의 매칭해 대표자명을 채우는 것은 동명이사·동명법인 오매칭 위험이
있으므로 권장하지 않는다.

## 서포트비에 적용할 때의 데이터 경계

추천하는 최소 데이터 형태는 다음과 같다.

- `representativeName`: 검증에 성공한 사용자의 입력값
- `representativeVerifiedAt`: 마지막 진위확인 시각
- `representativeVerificationSource`: 예: `nts_validate`
- `startDate`: 기본적으로 저장하지 않고 검증 요청에만 사용
- 사업자등록증 원본: OCR이 필수가 아니라면 수집하지 않음

현재 `biz_profiles`는 수정 시 새 행을 만들고 워크스페이스 포인터를 바꾸는 불변 스냅샷
구조다. 대표자명도 여기에 넣으면 기존 RFP가 참조하는 당시 사업자 프로필과 이후 변경분을
분리할 수 있다. 대표자가 바뀌면 새 대표자명·개업일자로 다시 검증해 새 프로필 행을 만드는
편이 현재 모델과 맞는다.

PG 상세 화면에 대표자명을 보낼지는 별도의 공개 경계 결정이다. 현재
[RfpBriefPanel](../components/inbox/RfpBriefPanel.tsx)은 대표자 행을 렌더링하지 않고,
[PG 상세 로더](../lib/server/rfp-detail-loader.ts)는 사업자 프로필에서 사업자번호와 등급만
남긴다. 표시를 구현하려면 저장뿐 아니라 이 서버 projection에 대표자명을 의도적으로
추가해야 한다. 반대로 오픈 게시판의 공개 whitelist에는 추가하지 않아야 한다. 공개 게시판
노출은 초대받아 상세를 보는 PG에게 제공하는 것보다 훨씬 넓은 별도 결정이다.

검증 장애 시에는 현재 `/status` 경로처럼 조용히 `verified: false`로 통과시킬지 별도 제품
결정이 필요하다. 대표자명을 화면에 사실처럼 표시하려면 최소한 `self_declared`와
`nts_verified`를 구분하고, 미검증 값을 검증된 값처럼 노출하지 않는 편이 안전하다.

## 개인정보·공개 범위 최소 검토

대표자명이 살아 있는 자연인의 이름이면 개인정보에 해당한다. 「개인정보 보호법」
[제2조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1030669293)는
성명으로 개인을 알아볼 수 있는 정보를 개인정보로 정의한다.

구현 전 최소한 다음을 확정해야 한다.

1. **처리 근거와 목적**: 수집·검증·저장에는 법 제15조에 맞는 처리 근거가 필요하다.
   개인정보보호위원회의
   [2025년 개인정보 처리방침 작성지침 안내](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS074&mCode=C020010000&nttId=11133)는
   회원서비스 운영 등 계약 체결·이행 정보는 동의 없이 처리할 수 있지만, 개인정보의
   제3자 제공은 계약 체결·이행 목적이어도 동의가 필요한 항목으로 설명한다. 초대 PG에게
   대표자명을 보여주는 행위는 제3자 제공에 해당할 수 있으므로, 다른 명확한 법적 근거를
   확인하지 못했다면 공개 동의와 법률 검토 없이 자동 노출하지 않는다.
2. **최소수집**: 법
   [제16조](https://www.law.go.kr/lsInfoP.do?lsiSeq=173223)는 목적에 필요한 최소한의
   개인정보만 수집하도록 하고 그 최소성의 입증책임을 개인정보처리자에게 둔다. 검증에만
   필요한 개업일자와 OCR 원본을 계속 저장하지 않는 이유다.
3. **처리방침과 제3자 제공 고지**: 법
   [제30조](https://law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1033214957)는 처리 목적,
   보유기간, 제3자 제공, 파기절차·방법 등을 개인정보 처리방침에 포함하도록 한다.
   대표자명을 수집하거나 PG에게 노출한다면 현 처리방침의 수집 항목·목적·기간·제공받는
   범위를 함께 갱신해야 한다.
4. **보유 종료와 파기**: 법
   [제21조](https://law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1027063705)는 보유기간이
   지났거나 처리 목적을 달성해 불필요해진 개인정보를 지체 없이 파기하도록 한다.
   사업자등록증 원본을 받는 경우 특히 파기 시점과 복구 불가능한 삭제 방법을 먼저 정한다.

이 절은 구현 시 확인할 최소 체크리스트이며 법률 자문을 대신하지 않는다. 특히 `RFP 상세를
볼 수 있는 초대 PG`라는 수신자 범위와 계약·거래 검토 목적이 적법한 제3자 제공 근거를
충족하는지는 출시 전 법률 검토가 필요하다.

## 추천 구현 순서

1. 사업자 프로필 입력에 `대표자명`, `개업연월일`을 추가한다.
2. 서버 전용 NTS 클라이언트에 `/validate` 호출을 추가한다. API 키와 원문 입력은 로그·오류
   수집 도구에 남기지 않는다.
3. 쓰기 서비스가 `valid === '01'`과 반환 `status`를 함께 확인한 뒤 대표자명 및 검증
   메타데이터만 저장한다. `request_param.p_nm`은 사용자가 보낸 값과 일치하는지 방어적으로
   확인할 수는 있지만 조회값으로 사용하지 않는다.
4. 미검증 저하 정책과 대표자 변경·재검증 정책을 명시한다.
5. 초대 PG 상세 projection에만 필드를 추가하고 오픈 게시판 경계는 유지한다.
6. 개인정보 처리방침과 제3자 제공 동의/고지를 먼저 정비한 뒤 화면 노출을 연다.

코드 변경 범위는 클라이언트 한 파일로 끝나지 않는다. 타입·DB migration·repository 매핑,
가입/설정 폼, 서버 쓰기 재검증, RFP 스냅샷 projection, PG 상세 응답, 개인정보 고지와 각각의
회귀 테스트가 함께 필요하다.
