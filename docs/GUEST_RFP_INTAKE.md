# 로그인 전 견적 작성과 이어쓰기

## 흐름

구매사 랜딩 → `/quote-start` → 홈페이지부터 기존 질문·첨부 작성 → 로그인/가입 → 이메일 인증·승인 → `/rfp-create?resume=guest` → 초안 선택 → 사업자 확인 → PG 추천 → 사용자의 최종 요청 순서다. 로그인된 구매사 CTA는 기존 `/rfp-create`를 연다. 공개 작성은 데모의 `guest` 모드가 아니다.

## 설계와 저장

- 질문 정의·완료 조건은 `content-questions.ts`, 렌더는 `RfpQuestionFlow`를 공유한다. `RfpDraftProvider`가 hook과 직접 store API 읽기를 같은 인스턴스로 연결한다. 기존 회원·데모 호출은 기본 store를 유지한다.
- `support-b-guest-rfp-v1` localStorage 키는 답변, 질문 위치, 초안 UUID, revision, 파일 메타데이터, 연결된 사용자/워크스페이스를 담는다. 첨부 원본은 `support-b-guest-rfp-files` IndexedDB의 `files` store에 별도 UUID로 저장한다. PDF/PNG/JPEG, 개당 20MB, 최대 5개다.
- 파일 메타데이터를 먼저 저장하고 IDB 트랜잭션 커밋 이후에만 저장 완료로 본다. 실패는 재시도·제거 경로를 제공한다. 완료 화면으로 이동하기 전 모든 원본을 확인한다. 브라우저 저장 공간을 확보하지 못하면 로그인 단계로 진행하지 않는다.
- `support-b-guest-rfp-resume=1`은 고정 내부 목적지만 선택한다. 로그인/가입의 `next`와 함께 사용하고, 인증·승인 후 기본 홈 진입도 소유자가 일치할 때 이어쓰기로 보낸다.
- 복원은 활성 구매사 페이지에서 명시적으로 초안을 선택한 뒤 사용자+워크스페이스에 고정한다. 기존 회원 초안은 그대로 남긴다. 인증 업로드는 성공한 파일마다 진행을 저장하고 부분 실패 시 성공분을 재사용한다. 기존 업로드가 유효하지 않으면 남겨둔 원본에서 다시 전송한다.
- 복원이 성공하면 홈 자동 이동 표식을 소비하고 답변·첨부는 유지한다. 발송 성공 응답이 유실됐을 때는 같은 워크스페이스·요청 키의 ready 첨부 ID를 유지해 기존 멱등 결과를 복구한다. 다른 요청이나 워크스페이스에 연결된 첨부는 이 경로로 가져오지 않는다.
- 최종 발송 직전 첨부와 actor를 다시 확인한다. 서버 액션은 기존 도메인 검증·멱등 키를 사용한다. 발송 성공 또는 명시적 삭제 때 로컬 메타데이터·원본을 정리한다. 첨부 없는 요청도 자동 제출하지 않는다.
- 정리는 초안 ID와 revision이 현재 저장값과 같을 때만 진행한다. 오래된 화면은 다른 탭의 새 초안이나 새 답변을 삭제하지 않으며, 이미 저장된 초안이 삭제되면 오래된 탭의 입력으로 되살리지 않는다.

같은 브라우저·구매사 호스트가 보존 범위다. 다른 기기/호스트 동기화, 자동 만료, 브라우저 데이터 삭제/eviction 이후 복구는 지원하지 않는다. localStorage와 IDB는 하나의 트랜잭션이 아니므로 메타데이터가 가리키는 원본이 없으면 제출을 막는다. 삭제 중 브라우저가 닫히면 원본 일부가 로컬에 남을 수 있다. 원격 업로드는 기존 첨부 수명 관리 정책을 따른다.

## 운영 이벤트와 공개 경계

공개 업종 목록은 `id/name/mccCode`만 SELECT한다. PG ID/정책은 인증된 추천 단계에서만 조회한다. `/quote-start`는 정확일치 인증 예외이며 noindex/nofollow다.

`POST /api/guest-rfp/events`는 홈페이지 답변 다음 이동 때 `started`, 전체 답변·원본 저장 후 인증 선택 화면으로 이동할 때 `completed`를 받는다. 두 이벤트는 초안 UUID로 연결한다. 서버 strict 스키마와 명시적 클라이언트 필드 구성이 홈페이지·업종·제목·계약 유형·첨부 개수만 허용한다. 상세 방어와 한계는 [위협 모델 §7](THREAT_MODEL.md#7-로그인-전-견적-작성-2026-10-11)을 따른다.

`guest_rfp_events` 복합 PK로 전송 전에 선점한다. 결과는 `claimed`(미확정), `sent`, `failed`, `skipped`(웹훅 미설정)다. 실패를 사용자 업무에 전파하지 않으며 자동 재전송하지 않는다. 외부 Slack과 DB를 원자 커밋할 수 없으므로 중복 억제를 우선한 최대 한 번 시도이며, 정확히 한 번 도착을 보장하지 않는다. `guest_rfp.slack_failed`·`guest_rfp.event_failed` 로그를 확인한다. 요약 원문은 DB 이벤트 행에 보관하지 않는다.

## 배포·롤백

1. 앱 배포 **전에** `scripts/migrations/20261011-guest-rfp-events.sql`을 적용한다. 기존 테이블 데이터는 변경하지 않는다.
2. `guest_rfp_events`의 `(draft_id,event)` PK와 event/result CHECK 제약을 확인한다. 기존 `SLACK_WEBHOOK_URL`을 사용하며 신규 환경변수는 없다.
3. 앱을 배포하고 공개 작성·로그인 복귀·두 이벤트 결과를 확인한다. 운영 smoke는 실제 Slack 알림을 만들므로 의도된 테스트 초안으로 실행한다.
4. 롤백 시 이벤트 테이블을 유지한다. 행을 지우면 이전 초안의 재시도가 중복 알림을 만들 수 있다. 사용자의 브라우저 저장 데이터는 서버 롤백으로 삭제하지 않는다.

이 작업에서는 격리된 테스트 DB에 스키마를 적용했으며 운영 DB 변경·배포·실제 Slack 발송은 수행하지 않았다.

## 검증

단위/컴포넌트 테스트는 초안 격리·저장 오류·낡은 탭·계정/워크스페이스 고정, 첨부 부분 성공·원본 유실, 회원 초안 충돌, 인증 복귀, 공개 projection, 이벤트 중복·입력/Origin/크기·rate limit·Slack 실패를 확인한다. DB 테스트는 동시 claim과 명시적 공개 projection을 검사한다.

`e2e/guest-rfp-intake.spec.ts`는 실제 브라우저 localStorage/IndexedDB를 사용해 키보드 작성·새로고침·로그인·최종 요청과 첨부 업로드 실패/재시도, 저장 공간 부족, 신규 가입·인증/승인 후 복원을 검사한다. 외부 R2 업로드와 SMS 발송은 응답을 대체하고, 이메일 링크 인증·운영자 승인은 테스트 DB 상태 전환으로 재현한다. 실제 R2·SMS·Slack 전달 자체를 검증한 결과로 해석하지 않는다.

### 2026-10-11 실행 기록

- 전체 단위 테스트: 834개 파일, 8,427개 통과(기존 skip·expected fail 별도). 이후 추가/수정분 포함 집중 실행: 66개 파일, 630개 통과.
- 타입 검사·lint·프로덕션 빌드 통과.
- Playwright 주요 6개 여정: 개발 서버와 빌드된 프로덕션 서버에서 모두 통과. 모바일 390×844와 데스크톱 1280×900 화면 및 첫 질문 Enter 이동 확인.
- 마이그레이션 SQL은 격리 스키마에서 두 번 실행하고 PK 중복·잘못된 event 거부를 확인한 후 롤백.
- 테스트 로그에 Next.js의 `The destination stream closed early`가 관측됐다. 여정과 DB 결과는 통과했지만 로그의 원인은 확정하지 않았다. 개발 서버의 `Invalid array length`는 프로덕션 실행에서 재현되지 않았다.
