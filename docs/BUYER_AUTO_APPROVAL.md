# 신규사업체 구매사 자동 승인

## 현재 상태

2026-10-25 결정으로 신규 구매사 가입·워크스페이스 생성의 자동 승인은 APICK 사업자 정보와 국세청 진위확인으로 검증한 개업 6개월 미만 사업체에만 적용한다. 보나페이 조회·판정은 제거했다. 과거 보나페이 승인 이력의 표시와 미인증 재가입 정리 호환은 유지한다. 개인/법인 모두 같은 기준이며 추가 사용자 입력을 받지 않는다. 간이과세만으로 승인하지 않는다. 기존 대기 건·PG 가입/합류·이메일 및 휴대폰 인증은 기존 절차를 유지한다.

## 조회와 판정

- 액션의 국세청 정상 영업 검증 이후 서비스가 buyer·명시적 검증 성공·정상 영업을 확인한다. 공개 번호 조회 액션에서는 APICK을 호출하지 않는다.
- 서버 환경변수 `APICK_API_KEY`가 있으면 조회 원본을 확보하며, 자동 승인에는 기존 `NTS_SERVICE_KEY`도 필요하다. 국세청 키가 없으면 성공한 APICK 원본만 저장하고 수동 심사로 접수한다. APICK 키 부재·조회 실패·검증 불충족도 수동 심사로 접수한다.
- [APICK 공식 명세](https://apick.app/dev_guide/biz_detail)의 `POST /rest/biz_detail`, Bearer 인증, multipart `biz_no`를 사용한다. 유료 조회이므로 운영 계정의 잔액·호출 조건을 확인한다.
- 승인에는 `api.success=true`, `data.success=1`, 사업자번호 일치, `상세정보확보=Y`와 공개 제한 없음이 필요하다. 개업일·대표명 누락이나 불명확한 제한 값은 승인하지 않는다.
- `설립일`은 후보 값이다. 사업자번호·개업일·대표명을 국세청 `/validate`로 검증해 `valid=01`, 응답 번호·요청 반향 일치, 정상 영업(`b_stt_cd=01`)을 모두 확인한다.
- 한국 날짜 기준 `개업일 <= 오늘 < 개업일 + 6개월`을 적용한다. 180일로 환산하지 않으며 대응 날짜가 없는 달은 말일로 맞춘다. 정확히 6개월이 된 날·미래·유효하지 않은 날짜는 제외한다.
- APICK와 국세청 진위확인은 각각 헤더·본문 포함 5초, 재시도·캐시·리다이렉트 없이 DB 트랜잭션 밖에서 실행한다. 이 두 요청의 예산은 최대 약 10초다.
- 승인 등급은 내부 정책상 `sole`, 출처는 `new_business_exception`이다. 실제 영세 등급을 공급자가 확인했다는 뜻이 아니다. 승인 이후 매일 재계산하거나 6개월 도달 시 자동 변경하지 않는다.

## 저장과 승인 경계

```text
인증된 휴대폰/로그인 세션 → 국세청 정상 영업 조회
  → 생성 서비스의 buyer + 검증 성공 + 정상 영업 확인
  → APICK 사업자 정보 조회
      성공 + 번호 일치 원본은 별도 조회 감사 대상으로 확보
  → 개업일·대표명 국세청 진위확인 + 개업 6개월 미만 판정
  → 한 DB 트랜잭션으로 신청·워크스페이스·멤버십·감사 저장
      조건 충족: sole/new_business_exception + active + approved
      그 외: 기존 심사 대기
      확보한 APICK 원본: 승인 여부와 무관하게 별도 조회 감사 저장
  → 커밋 후 기존 운영 알림, 이메일 인증 및 견적 복원 절차
```

APICK 성공·사업자번호 일치 응답의 원본 JSON 전체(`api`·`data`, 대표명 포함)를 기존 `admin_audit_logs`에 저장한다. `entity_type=verification_application`과 신청 ID로 연결하고 `action=workspace.apick_lookup`, `payload_json.after.response`에 보관한다. 자동 승인 여부와 무관하므로 개업 6개월 이상이거나 국세청 진위확인에 실패한 신청도 성공한 APICK 조회 원본은 남는다. 조회 실패·번호 불일치 응답은 이 원본 보관 대상이 아니다. 키·요청 헤더·국세청 원문은 저장하지 않는다. 원본은 관리자 감사 접근 경계 안에서만 사용하며 일반 구매사·PG 응답이나 운영 알림에 전달하지 않는다. 별도 DB 필드는 추가하지 않는다.

자동 승인 시에는 별도의 `actor=system:apick`, `action=workspace.auto_approve` 감사로 `outcome=new_business_confirmed`, 검증된 `openingDate`, `verifiedBy=nts_validate`, 조회 시각과 신청·워크스페이스 상태를 기록한다. 조회 감사만으로 자동 승인으로 해석하지 않는다. 감사 저장이 실패하면 전체 생성 트랜잭션이 롤백된다.

미인증 재가입 정리는 `system:apick`+`new_business_exception` 또는 과거 `system:bona-pay`+`api_confirmed`의 정확한 조합과 `sole`·본인 단독 admin·견적 없음인 active 구매사에 적용한다. 다른 멤버·기존 견적·수동 확인·정지 상태가 있으면 보존한다. 정확히 같은 게스트 초안 ID+HttpOnly 비밀값 재제출은 응답 유실 복구로 보존하며 그 밖의 재가입은 기존 초안을 폐기하고 계정을 교체한다. 워크스페이스 승인은 이메일 인증을 대체하지 않는다.

## 배포 순서

1. 공유 DB에 미적용된 `scripts/migrations/20261020-buyer-auto-approval.sql`과 `scripts/migrations/20261025-new-business-approval.sql`을 실행하고 커밋한다. 새 enum을 추가할 뿐 기존 데이터 UPDATE는 없다. 같은 트랜잭션에서 새 enum 값을 사용하지 않는다.
2. 관리자 서비스를 배포한다. 신규사업체 예외·개업일·국세청 확인과 별도 APICK 조회 원본을 표시하며 과거 `api_confirmed` 이력도 유지한다.
3. 구매사 서버에 APICK·국세청 키를 설정하고 서비스를 배포한다. 로컬 키 설정은 운영 설정을 대신하지 않는다. 보나페이 조회가 없고 신규사업체 조건만 자동 승인하는지 확인한다.

## 검증과 운영 확인

2026-10-25 작업에서 사용자 지정 사업자의 APICK 개업일 반환과 국세청 진위 일치·정상 영업을 실제 확인했다. 단일 사례이며 모든 신규사업자의 정보 제공을 보장하지 않는다. 실측 원문·대표명·키를 코드 저장소에 남기지 않는다. 운영 신청에 연결되는 원본 감사 보관과 개발 검증 자료는 구분한다.

- [ ] APICK 운영 계정의 잔액·호출 조건과 정보 제공 범위를 확인한다.
- [ ] 키 부재·번호 불일치·누락·장애·국세청 불일치·6개월 경계가 수동 심사로 남는지 확인한다.
- [ ] 성공·번호 일치 APICK 원본이 승인/대기 신청 모두에 연결되고 별도 조회 사건으로 표시되는지 확인한다.
- [ ] 관리자 승인 이력·과거 보나페이 이력·이메일 인증 후 견적 복원을 확인한다.

관련 자동 검증은 `lib/server/buyer-approval/new-business.test.ts`, `lib/server/services/__tests__/buyer-auto-approval.test.ts`, `scripts/migrations/__tests__/buyer-auto-approval.test.ts`와 관리자 `components/__tests__/WorkspaceReviewInfo.test.tsx`가 담당한다. 과거 보나페이 성공 응답에 기반한 이력은 신규 조회 계약으로 해석하지 않는다.

## 중지·복구

`APICK_API_KEY`를 제거하고 앱을 재시작하면 신규 자동 승인을 중지한다. 이미 승인된 계정·과거 감사·enum 값은 보존하고 기존 대기 건은 일괄 변경하지 않는다. 감사/가입 트랜잭션 오류는 전체 생성이 롤백되므로 기존 재시도 경로를 사용한다.
